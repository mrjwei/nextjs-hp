デザインシステムはルールの集まりです。トークンを使う、コンポーネントをデタッチしない、色だけで意味を伝えない。Figmaでは、こうしたルールはガイドラインのページと人の頭の中にあり、みんなが覚えている間だけ守られます。

リポジトリなら、ルールを強制できます。エージェントが入力の多くを担うようになると、これがいっそう重要になります。エージェントは与えられたルールに従うのはとても得意ですが、与えられていないルールを推測するのはとても苦手だからです。以下のセットアップは、リポジトリ一つにつき1時間ほどで終わります。これさえ済めば、[パート1](/ja/posts/design-in-git/design-in-git-part-1-explore-privately-critique-in-public)の日々のループはブランチ → 作る → 見る → `/code-review` → PRだけになり、まずいセッションがやらかせる最悪のことも、まずいプルリクエストを開くことくらいになります。

これは*Design in Git*のパート2です。レビューは[パート3](/ja/posts/design-in-git/design-in-git-part-3-design-crit-with-a-paper-trail)で扱います。GitHubとClaude Codeに関する内容は、2026年10月26日にドキュメントと照らし合わせて確認しました。

## デザインシステムのリポジトリに入っているもの

私があるスタートアップのプロダクトのデザインシステム用に作ったものは、小さなモノレポ(複数のパッケージを一つにまとめたリポジトリ)です。部分ごとに答える問いが違うので、この形は真似する価値があります。

```
packages/tokens            DTCG token file: the only place a colour, size or radius value lives
packages/ui                the component library, built on shadcn/ui
packages/eslint-plugin-ds  one lint rule: no hardcoded values (see step 6)
apps/docs                  the design system site, generated from tokens and components
docs/decisions/            one file per design decision: D-001, D-002 …
```

トークンファイルは[Design Tokens Community Group](https://www.designtokens.org/)の形式を使っているので、同じ値をFigmaとコードの間で行き来させられます。ビルドのステップでこれがCSS変数と、ドキュメントサイトの表に使うTypeScriptのリストに変換されます。生成された出力は手で編集することも、コミットすることもありません。

## 0 · 最初のpushの前に:既存のリポジトリを整える

プロジェクトがすでにローカルにあり、リモートがない場合:

```bash
git status                       # commit or stash work in progress first
git worktree prune               # drop stale worktrees
git config user.email            # must be a verified email on my GitHub account
git log --all -p | grep -iE 'secret|token|AKIA|password' | head   # quick scan for leaked secrets in history
```

(デザインシステムのリポジトリでは、最後の行がデザインの*トークン*にも片っ端からマッチします。それは読み飛ばしてください。探しているのは鍵とパスワードです。)

次にリポジトリを作り、既存の履歴をpushします。

```bash
gh repo create my-design-system --private --source=. --remote=origin
git push -u origin --all         # every local branch, not just the current one
```

GitHub側でREADMEやライセンスを追加しないでください。`--source=.` はローカルの履歴をそのまま使うので、中身の入ったリポジトリだとそれと衝突します。

## 1 · ツールにサインインする

```bash
brew install gh && gh auth login
claude                           # sign in on first run (/login)
```

ClaudeにFigmaを読み書きさせるなら、同じノートPCのClaude CodeでFigma MCPサーバーをつなぎ、Figmaデスクトップアプリを開いておきます。この接続は私のマシンの上にしか存在しません。Figmaのステップを決してクラウドで動かさないのはそのためです。

## 2 · Claudeにシステムを教える:CLAUDE.md

Claude Codeの中で`/init`を実行すると、たたき台の`CLAUDE.md`が生成されます。思い切って削ってから、コミットします。Claudeのツールはどれも、実行のたびにこのファイルを読みます(ローカルでも、Actionでも、クラウドセッションでも)。つまり一行一行が、ずっとトークンを消費し続けます。

デザインシステムにとって、このファイルは、ガイドラインのページがエージェントに実際に守られるものに変わる場所です。私のものを短くし、この記事用に少し手を加えたものがこちらです。*Review rules*のセクションと、*Flag rather than decide*の最初の項目は、私のファイルにある行ではなく、提案として加えたものです。

```markdown
# Design system
## Where things live
- packages/tokens/src/tokens.json (DTCG) is the only place values live.
- packages/tokens/dist/ is generated. Never hand-edit it.
- packages/ui: components. Never hardcode a colour, size, radius or type value.
- docs/decisions/: one record per decision. Never edit one in place; supersede it.
## Figma
- Figma is the source of truth; this code is the implementation, not the spec.
- Conflicts: Figma wins, but say so out loud. Never silently follow the code.
- Figma sync is report-only unless explicitly run with --write.
## Per component
1. Read it from Figma. 2. Build it. 3. Compare with the Figma frame before declaring done:
   a screenshot, not a clean build. 4. Push it back to Figma. 5. Commit.
## Flag rather than decide
- Any change to a token value or name
- Any component whose accessible behaviour differs from the Figma spec
- Anything that contradicts an active decision record
## Review rules
- Colour is never the only signal of state
- New components need a Storybook story and a docs page
```

このうち3つの行が、仕事のほとんどを担っています。

- **「Figma wins, but say so out loud.」(Figmaが優先。ただし、そのことを口に出して言う)** Claudeは、デザインファイルとコードが食い違う箇所に必ず出くわします。この一行がなければ、黙ってどちらかを選びます。あれば、食い違いの一つひとつが目に見える問いになります。
- **「Flag rather than decide.」(決めずに指摘する)** 私のリポジトリで、すべてのコンポーネントの余白を黙って変えてしまうところだったスペーシングトークンの衝突を捕まえたのが、この一行です(いきさつは[ハブの記事](/ja/posts/design-in-git/i-was-reinventing-git-in-figma)にあります)。
- **「A screenshot, not a clean build.」(クリーンなビルドではなく、スクリーンショット)** エージェントにとっての完了の定義は「コンパイルが通る」こと。デザイナーにとっては「見た目が正しい」ことです。自分の定義を書いておきましょう。

レビューのルールも、`REVIEW.md`だけでなくここに書きます。ローカルの`/code-review`は`CLAUDE.md`を読みますが、`REVIEW.md`は読まないからです(詳しくは[パート3](/ja/posts/design-in-git/design-in-git-part-3-design-crit-with-a-paper-trail)で説明します)。

## 3 · ルールセットでmainを守る

`main`は公開されたデザインシステムです。デザインレビューを経ずに本番の画面に何かが載ってはならないのと同じように、`main`にもプルリクエストを経ずに何かが届いてはなりません。

**まずプランを確認:** **プライベート**リポジトリでルールセットを使うには、GitHub Pro、Team、Enterpriseのいずれかが必要です(学生は[GitHub Student Developer Pack](https://education.github.com/pack)でProを無料で使えます)。GitHub Freeでは、パブリックリポジトリでしか機能しません。

Settings → Rules → Rulesets → **New branch ruleset**:

| 項目 | 設定 | 理由 |
|---|---|---|
| Ruleset name | `protect-main` | 名前は何でもよい |
| Enforcement status | **Active** | デフォルトの*Disabled*では何も強制されない |
| Bypass list | 空 | 誰も(私もClaudeも)`main`に直接pushしない |
| Target branches | **Add target → Include default branch** | `main`を対象にし、名前を変えても外れない |

| ブランチのルール | 一人 | チーム | 理由 |
|---|---|---|---|
| Restrict creations / updates | ☐ | ☐ | *Restrict updates*はマージまでブロックしてしまう |
| Restrict deletions | ☑ | ☑ | `main`が削除されるのを防ぐ |
| Require linear history | ☑ | ☑ | スカッシュのみの運用と揃う:PR一つにつきコミット一つ |
| Require signed commits | ☐ | 状況による | 自分のコミットに署名していないと、自分がブロックされる |
| **Require a pull request before merging** | ☑ | ☑ | 要となるルール。オプションは下に |
| Require status checks to pass | CIができたら☑ | ☑ | チェックは一度実行されたあとでないと名前で選べない |
| Block force pushes | ☑ | ☑ | 履歴の書き換えを防ぐ |
| Copilot code review | ☐ | ☐ | ここではClaudeがレビュアー |

**Require a pull request before merging**の下:

| オプション | 一人 | チーム |
|---|---|---|
| Required approvals | **0**:GitHubでは自分のPRを自分で承認できないので、1以上にすると自分が締め出される | 1以上 |
| Dismiss stale approvals、Code Owners review、approval of most recent push | ☐ | チームの好みで |
| **Require conversation resolution before merging** | ☑ | ☑ |
| Allowed merge methods | **Squash**のみ | チームの選択 |

**チームなら、デザインにCode Owners reviewを有効にしましょう。** `CODEOWNERS`ファイルで、`packages/tokens/`や`docs/decisions/`以下の変更にはデザイナーの承認が必要だと指定できます。リポジトリ自身が「デザインのことはデザインが承認する」と言っているわけで、どんなプロセス文書よりも強い保証です。

*Require conversation resolution*は、一人のPRをチームのPRのように感じさせてくれる習慣です。Claudeのものも含め、すべてのレビューコメントを解決しないとマージできません。

これと組み合わせる設定がリポジトリに二つあります(Settings → General → Pull Requests)。**squash merging**だけを許可し、**Automatically delete head branches**を有効にします。

**テスト:** `main`で小さな変更をコミットし、`git push origin main`を実行します。PRを開くよう促すメッセージとともに拒否されるはずです。

## 4 · Claudeをつなぐ:/install-github-app

リポジトリの中で、Claude Codeから実行します(`gh`へのサインインと、リポジトリの管理者権限が必要です)。Claude GitHub Appをインストールし、シークレットを保存し、ワークフローのファイルを入れたブランチをpushしてくれるので、あとはPRとして開くだけです。

**認証の選択:**

| シークレット | 請求先 | 向いている用途 |
|---|---|---|
| `ANTHROPIC_API_KEY` | Claude Console(APIの請求) | 共有のリポジトリや組織のリポジトリ |
| `CLAUDE_CODE_OAUTH_TOKEN`(`claude setup-token`で取得) | 私のProまたはMaxのプラン | 個人のリポジトリ |

聞かれたら、私は両方のワークフローを選びます。`@claude`のワークフローと、レビューのワークフローです。

## 5 · セットアップのPRをマージして、テストする

ワークフローは`main`に入って初めて動きます。開かれたPRをマージしてから、どれかのPRにコメントします。

```text
@claude explain this diff in terms a designer would use
```

## 6 · デザインのチェックも含めて、CIを追加する

CI(継続的インテグレーション)は、プルリクエストのたびにチェックを走らせ、結果を赤か緑で示します。たいていのリポジトリでは、ビルド、lint、型チェックのことです。デザインシステムでは、デザインのルールを破れないものにできる場所でもあります。

私のCIは、インストール、ビルド、lint、型チェックの4つを実行します。

```yaml
# .github/workflows/ci.yml
name: CI

on:
  pull_request:
  push:
    branches: [main]

jobs:
  build-lint-typecheck:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: pnpm
      - run: pnpm install --frozen-lockfile
      - run: pnpm build
      - run: pnpm lint
      - run: pnpm typecheck
```

デザインのチェックは`pnpm lint`の中に隠れています。このリポジトリには`no-token-escape`という小さな独自のlintルールが一つあり、Tailwindのクラスの中に値がハードコードされていると失敗します。`p-[14px]`、`text-[#0c66e4]`、`rounded-[8px]`のようなものです。`rounded-[min(var(--radius-md),10px)]`のようにトークンを使う値は許可されます。トークンがあるべき場所にハードコードされた値は、デザインシステムが崩れていく最小の単位で、コードなら簡単に検出できます。Figmaでは、見つけられるとしても目視です。

ビルドのステップも重要です。トークンファイルからトークンを生成し直すので、壊れたトークンファイルや矛盾したトークンファイルは、ドキュメントサイトに届く前にPRを失敗させます。

**CIにチェックできないこと:** 見た目です。このリポジトリにはビジュアルリグレッションテストがないので、見た目の確認はインナーループに残ります(パート1のステップ4)。チームに予算があれば、スクリーンショット比較のテストが自然な次の層です。

CIが一度実行されれば、そのジョブ名(`build-lint-typecheck`)をルールセットの**required status check**として選べます。赤いチェックは、自動修正(auto-fix)が反応するものでもあります(パート3)。

## 7 · クラウドセッションと自動修正

[claude.ai/code](https://claude.ai/code)でGitHubをつなぎ、[Claude GitHub App](https://github.com/apps/claude)が**Only select repositories → このリポジトリ**でインストールされていることを確認します(代わりに`/web-setup`でローカルの`gh`のトークンを送ることもできますが、自動修正にはやはりアプリが必要です)。次に、クラウド環境を設定します。

| 設定 | 私の選択 | 理由 |
|---|---|---|
| Network access | **Trusted**(デフォルト) | パッケージレジストリや一般的な開発用ホストにはつながり、任意のホストにはつながらない |
| Environment variables | クラウドプロバイダーや本番の認証情報は**入れない** | クラウドセッションが本番のインフラに触れられてはならない |
| Setup script | 必要になるまで空 | 各タスクに必要なものは、プロジェクト自身の`pnpm`スクリプトがインストールする |

クラウドセッションからはFigmaに届かないことを覚えておいてください。任せるのは、リポジトリの中だけで完結するタスクです。ストーリー、ドキュメントのページ、翻訳、すでに仕様が決まっているバリアントなど。

`/install-github-app`が作る2つのワークフローファイルは、何が動いているのかを知るために一度は読んでおく価値があります。

### `@claude`のワークフロー(`.github/workflows/claude.yml`)

```yaml
name: Claude Code
on:
  issue_comment:
    types: [created]               # PR and issue conversation comments
  pull_request_review_comment:
    types: [created]               # inline diff comments
jobs:
  claude:
    if: contains(github.event.comment.body, '@claude')   # don't start a runner for every comment
    runs-on: ubuntu-latest
    permissions:
      contents: write
      pull-requests: write
      issues: write
      id-token: write              # needed for the default GitHub App auth
      actions: read                # lets Claude read CI results
    steps:
      - uses: actions/checkout@v6
        with:
          fetch-depth: 1
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          # or: claude_code_oauth_token: ${{ secrets.CLAUDE_CODE_OAUTH_TOKEN }}
          # trigger_phrase: "@claude"   # change it if managed Code Review also runs
          # claude_args: --max-turns 5
```

この最小限の版は、コメントだけを待ち受けます。新しいIssueの本文やレビューのまとめをきっかけに動かしたいなら、より充実した[`examples/claude.yml`](https://github.com/anthropics/claude-code-action/blob/main/examples/claude.yml)から始めてください。

### レビューのワークフロー(`.github/workflows/claude-code-review.yml`)

```yaml
name: Code Review
on:
  pull_request:
    types: [opened, synchronize, ready_for_review, reopened]
jobs:
  review:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: read
      issues: read
      id-token: write
    steps:
      - uses: actions/checkout@v6
        with:
          fetch-depth: 1
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          plugin_marketplaces: "https://github.com/anthropics/claude-code.git"
          plugins: "code-review@claude-code-plugins"
          prompt: "/code-review:code-review --comment ${{ github.repository }}/pull/${{ github.event.pull_request.number }}"
          claude_args: '--allowedTools "mcp__github_inline_comment__create_inline_comment"'
```

同じActionに、モードが二つあります。**`prompt`なし** = 対話モード(`@claude`を待つ)。**`prompt`あり** = 自動モード(イベントで動く)。レビューをPRに投稿させているのは`--comment`で、それを許可しているのが`claude_args`の行です。

## セットアップがうまくいかないとき

| 症状 | ありがちな原因 → 対処 |
|---|---|
| ルールセットを保存したのに、`main`がまだ直接のpushを受け付ける | Enforcementが*Disabled*のまま、またはGitHub Freeのプライベートリポジトリ |
| 自分のPRをマージできない | 一人のリポジトリでRequired approvalsが0より大きい → 0にする |
| 失敗しているチェックがないのに、マージボタンがブロックされている | *Require conversation resolution*が有効 → 残っているスレッドを解決する |
| コンポーネントがスタイルなしで表示されるのに、ビルドは通る | モノレポでは、Tailwind v4がコンポーネントのパッケージをクラス名のスキャン対象にしないことがある → アプリのCSSにそのパッケージ用の`@source`を明示的に追加する。スクリーンショットなら気づけるが、CIでは気づけない |
| Claudeのコミットに対してCIが動かない | `github_token: ${{ secrets.GITHUB_TOKEN }}`が設定されている。GitHubはそのトークンからはワークフローを起動しない → 削除して、ActionがClaude Appを使うようにする |
| `claude --cloud`が古いコードで作業している | 作業コピーではなく、GitHubのブランチをクローンしている → 先にpushする |
| クラウドセッションがFigmaのファイルを読めない | 想定どおり:Figma MCPの接続はローカルにある → FigmaのステップはノートPCで行う |

## まずはサンドボックスのリポジトリで練習する

私がこれを腹落ちさせられたのは、使い捨てのリポジトリと、わざと退屈な変更を続けた1週間のおかげです。デザイナーなら、それをデザインの変更にするのがいいと思います。

1. 小さなトークンファイルとコンポーネント2つだけのサンドボックスのリポジトリで、上のセットアップを行う。
2. `git`と`gh`だけで小さなPRを3つ作る(トークンの名前を変える、角丸を変える、ドキュメントのタイポを直す)。ブランチ → push → PR → マージが体に染みつくまで。
3. `/plan`でコンポーネントのバリアントを追加し、ブラウザで見てから、`/code-review`を`low`と`high`で実行して、それぞれが見つけるものを比べる。
4. わざと色をハードコードして、lintのチェックが赤くなるのを見る。それから`/autofix-pr`で直す。
5. レビューのワークフローにコメントさせ、`@claude`で修正を試し、スレッドを解決する。

どの部品も、それだけでは特に気の利いたものではありません。けれど組み合わせると、デザインシステムへのすべての変更が、私のものもClaudeのものも、チェックとレビューを経たプルリクエストを通って`main`に届くようになります。それが[パート1](/ja/posts/design-in-git/design-in-git-part-1-explore-privately-critique-in-public)のアウターループであり、それを記憶ではなくリポジトリが強制してくれるのです。
