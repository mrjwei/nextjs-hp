Most of us have thousands of photos and no real way to find anything in them. What people actually want is to ask for something like "find me the photos of my dog", or to turn an album into a narrated slideshow, and have it just work. That's a findability problem, not a storage one.

Strobe, the photo-sharing app I [built on AWS](/projects/strobe/migrating-a-traditional-monolithic-backend-to-a-cloud-native-serverless-microservices-architecture) earlier in my cloud computing course, stores those photos but can't do any of that. Strobe Assistant is my answer: a conversational agent that searches a user's own photos and posts in plain language, finds photos similar to one they attach, writes narrated albums, and puts together an "on this day" retrospective every morning. It builds on Strobe's existing infrastructure rather than changing it.

This post is the overview: what I built, the decisions that mattered, the numbers, what broke and what I'd change. Four companion posts each take one of those apart.

The system has three planes, each with its own shape of traffic. The highlighted services are the ones I built and deployed; the rest are managed AWS services or the existing Strobe stack.

<figure style={{ textAlign: "center" }}>
  <img src="/strobe-assistant-extending-strobe-with-an-ai-agent/overview-1-architecture.svg" alt="Strobe Assistant architecture: three planes built on the existing Strobe stack" style={{ marginBottom: "8px" }} />

- **The conversation (synchronous).** The browser connects through an Application Load Balancer to three services on ECS Fargate: a web client, an agent that runs the conversation on Gemma 3 12B in Amazon Bedrock, and an MCP server that exposes the tools. The tools search two vector indexes in S3 Vectors and read posts and images through Strobe's own API.
- **Ingestion (asynchronous).** An upload lands in S3, which queues an event in SQS. A worker Lambda embeds and classifies the photo a few seconds later, so the upload itself never waits.
- **The scheduled run (autonomous).** Every morning at 7, EventBridge Scheduler starts a Lambda that signs in as an enrolled user and talks to the same agent as any chat client, with the same checks. An unattended job gets no special access.

## Five decisions that mattered

| Decision | Alternative | Why | What it cost |
|---|---|---|---|
| The user's ID comes from the verified token, inside the MCP server | The user ID as a tool argument | The model can't change what it never controls, so an injected caption can't widen a search | Nothing worth naming. Everything else hangs off this rule |
| The agent runs on Fargate | Lambda behind an API Gateway WebSocket API | A turn is a long-lived streaming WebSocket with an open MCP client. API Gateway's 29-second integration limit and cold starts don't fit | About $11 a month per always-on task, and no scaling to zero |
| The MCP server is its own service | A library inside the agent, or a subprocess | It's the security boundary, it scales differently from the agent, and any agent can reuse it | One HTTPS hop per tool call (a search takes 0.52 s at the median) |
| SQS sits between S3 and the worker | S3 invoking the worker directly | Bursts of uploads wait instead of failing against the Bedrock quota, and I control retries, the DLQ and redrive | At-least-once delivery, so every write has to be idempotent |
| Two indexes, fused by rank | One multimodal index | Titan Multimodal reads 256 tokens of English; posts run to 5,000 characters in any language | Two embeddings and two queries per search, and an MRR cost of 0.03 |

## Results

All numbers come from an evaluation harness that runs against the deployed system.

**Retrieval** (25 questions over 49 of my own photos, with 95% bootstrap intervals):

| Configuration | recall@5 | MRR |
|---|---|---|
| Image index only | 0.75 [0.65–0.85] | 0.92 [0.84–0.98] |
| Text index only | 0.08 [0.02–0.16] | 0.16 [0.04–0.32] |
| Fused | 0.77 [0.65–0.88] | 0.89 [0.79–0.97] |

Overall, fusion makes no measurable difference to recall, but on questions about what I'd *written*, it adds 0.37 recall@5 (paired CI +0.17 to +0.50). The small MRR loss turned out to be a labelling artefact.

**Speed and cost per turn.** A chat turn takes 3.4 s at the median and 9.2 s at the 95th percentile, over 12 logged turns. It costs about $0.0004, 96% of it model tokens, so a ten-turn conversation costs under half a cent.

**Idle cost.** About $51 a month before anyone talks to it: $32 for three always-on Fargate tasks, $18 for the load balancer and $0.40 for one secret. That's the price of a streaming WebSocket agent. Running the three services as one task with three containers would cut the Fargate share to about $11, but they'd scale and fail together. I chose isolation, because one of the three is the security boundary.

**Ingestion.** About $0.19 per 1,000 photos. The vision model's caption, not the embedding, is the expensive half.

**Security.** I planted a prompt injection in a post and ran ten checks across the MCP server and the agent. All ten passed: the payload reached the model, but a second account couldn't search or fetch the first account's photos, and neither the system prompt nor the user's ID leaked.

## What broke

- **A small model that wouldn't call tools, and a 15-second reply.** Gemma 3 wrote its tool calls as text, and later spent 15 seconds retyping a URL to show one photo. → [Making a Small Model Use Tools, and the 15-Second URL](/projects/strobe/making-a-small-model-use-tools-and-the-15-second-url)
- **Every phone photo in the dead-letter queue.** Titan Multimodal caps images at 2,048 pixels a side, whatever the file size. → [Own the Buffer: 18 Dead-Lettered Photos](/projects/strobe/own-the-buffer-18-dead-lettered-photos)
- **An agent that believed its own memory.** Early run summaries recorded answers the model had made up, and later sessions repeated them as fact. → [When the RAG Corpus Is User-Generated: Keeping an Agent's Tools Out of a Caption's Reach](/projects/strobe/when-the-rag-corpus-is-user-generated)
- **A fusion "loss" that wasn't one.** The MRR drop came from duplicate photos my labels didn't know about. → [Measuring Retrieval Honestly with n = 25](/projects/strobe/measuring-retrieval-honestly-with-n-25)

## What I'd change

- **Infrastructure as code.** I configured most resources in the console, which makes the setup hard to rebuild, review or version.
- **An external session store.** The agent keeps sessions in memory, so it can't scale past one task, and a redeploy drops conversations in progress.
- **Re-ranking**, and fusing at the post level so that a photo and its own post's text can reinforce each other.
- **One task with three containers**, if cost mattered more than isolation.
- **A model with native tool calling**, given the choice. Switching is one configuration value.
