A design system is a set of rules: use the tokens, don't detach the component, colour never carries meaning on its own. In Figma, those rules live in a guidelines page and in people's heads, and they hold for as long as everyone remembers them.

In a repository, the rules can be enforced. That matters more once an agent is doing a lot of the typing, because an agent is very good at following rules it's been given and very bad at guessing the ones it hasn't. The setup below takes about an hour per repo. After it, the everyday loop from [Part 1](/posts/design-in-git/design-in-git-part-1-explore-privately-critique-in-public) is just branch → build → look → `/code-review` → PR, and the worst a bad session can do is open a bad pull request.

This is part 2 of *Design in Git*. [Part 3](/posts/design-in-git/design-in-git-part-3-design-crit-with-a-paper-trail) covers reviews. The GitHub and Claude Code details were checked against the docs on 26 October 2026.

## What's in a design-system repo

Mine, for a startup product's design system, is a small monorepo (one repository holding several packages). The shape is worth copying because each part answers a different question:

```
packages/tokens            DTCG token file: the only place a colour, size or radius value lives
packages/ui                the component library, built on shadcn/ui
packages/eslint-plugin-ds  one lint rule: no hardcoded values (see step 6)
apps/docs                  the design system site, generated from tokens and components
docs/decisions/            one file per design decision: D-001, D-002 …
```

The token file uses the [Design Tokens Community Group](https://www.designtokens.org/) format, so the same values can travel between Figma and code. A build step turns it into CSS variables and a TypeScript list that the docs site uses for its tables. The generated output is never edited by hand and never committed.

## 0 · Before the first push: tidy an existing repo

If the project already exists locally with no remote:

```bash
git status                       # commit or stash work in progress first
git worktree prune               # drop stale worktrees
git config user.email            # must be a verified email on my GitHub account
git log --all -p | grep -iE 'secret|token|AKIA|password' | head   # quick scan for leaked secrets in history
```

(In a design-system repo, that last line will also match every design *token*. Skim past them; you're looking for keys and passwords.)

Then create the repo and push the existing history:

```bash
gh repo create my-design-system --private --source=. --remote=origin
git push -u origin --all         # every local branch, not just the current one
```

Don't add a README or licence on GitHub: `--source=.` reuses the local history, and a pre-filled repo would conflict with it.

## 1 · Tools signed in

```bash
brew install gh && gh auth login
claude                           # sign in on first run (/login)
```

If Claude will read from or write to Figma, connect the Figma MCP server in Claude Code on the same laptop, with the Figma desktop app open. That connection only exists on my machine, which is why Figma steps never run in the cloud.

## 2 · Teach Claude the system: CLAUDE.md

`/init` inside Claude Code generates a starter `CLAUDE.md`. Trim it hard, then commit it. Every Claude tool reads it on every run (locally, in the Action and in cloud sessions), so every line costs tokens forever.

For a design system, this file is where the guidelines page becomes something an agent actually follows. Here's a shortened version of mine, lightly adapted for this post. The *Review rules* section and the first *Flag rather than decide* item are suggestions I've added, not lines from my file:

```markdown
# Design system
## Where things live
- packages/tokens/src/tokens.json (DTCG) is the only place values live.
- packages/tokens/dist/ is generated. Never hand-edit it.
- packages/ui: components. Never hardcode a colour, size, radius or type value.
- docs/decisions/: one record per decision. Never edit one in place; supersede it.
## Figma
- Figma is the source of truth; this code is the implementation, not the spec.
- Conflicts: Figma wins, but say so out loud. Never silently follow the code.
- Figma sync is report-only unless explicitly run with --write.
## Per component
1. Read it from Figma. 2. Build it. 3. Compare with the Figma frame before declaring done:
   a screenshot, not a clean build. 4. Push it back to Figma. 5. Commit.
## Flag rather than decide
- Any change to a token value or name
- Any component whose accessible behaviour differs from the Figma spec
- Anything that contradicts an active decision record
## Review rules
- Colour is never the only signal of state
- New components need a Storybook story and a docs page
```

Three lines in there do most of the work:

- **"Figma wins, but say so out loud."** Claude will hit places where the design file and the code disagree. Without this line, it quietly picks one. With it, every conflict becomes a visible question.
- **"Flag rather than decide."** This is the line that caught a spacing-token clash in my repo that would have silently changed the padding on every component ([the hub post](/posts/design-in-git/i-was-reinventing-git-in-figma) has the story).
- **"A screenshot, not a clean build."** An agent's definition of done is "it compiles". A designer's is "it looks right". Write yours down.

The review rules belong here too, not only in a `REVIEW.md`: local `/code-review` reads `CLAUDE.md` but not `REVIEW.md` ([Part 3](/posts/design-in-git/design-in-git-part-3-design-crit-with-a-paper-trail) explains).

## 3 · Protect main with a ruleset

`main` is the published design system. Nothing should reach it without passing through a pull request, the same way nothing should reach production screens without a crit.

**Plan check first:** rulesets on **private** repos need GitHub Pro, Team or Enterprise (students get Pro free with the [GitHub Student Developer Pack](https://education.github.com/pack)). On GitHub Free they only work on public repos.

Settings → Rules → Rulesets → **New branch ruleset**:

| Field | Setting | Why |
|---|---|---|
| Ruleset name | `protect-main` | Any name |
| Enforcement status | **Active** | The default, *Disabled*, enforces nothing |
| Bypass list | Empty | Nobody (not me, not Claude) pushes straight to `main` |
| Target branches | **Add target → Include default branch** | Targets `main` and survives a rename |

| Branch rule | Solo | Team | Why |
|---|---|---|---|
| Restrict creations / updates | ☐ | ☐ | *Restrict updates* would block merges too |
| Restrict deletions | ☑ | ☑ | Stops `main` being deleted |
| Require linear history | ☑ | ☑ | Matches squash-only: one commit per PR |
| Require signed commits | ☐ | depends | Blocks me unless my commits are signed |
| **Require a pull request before merging** | ☑ | ☑ | The key rule; options below |
| Require status checks to pass | ☑ once CI exists | ☑ | A check can only be picked by name after it has run once |
| Block force pushes | ☑ | ☑ | Stops history being rewritten |
| Copilot code review | ☐ | ☐ | Claude is the reviewer here |

Under **Require a pull request before merging**:

| Option | Solo | Team |
|---|---|---|
| Required approvals | **0**: GitHub won't let me approve my own PR, so 1 or more locks me out | 1+ |
| Dismiss stale approvals, Code Owners review, approval of most recent push | ☐ | As the team prefers |
| **Require conversation resolution before merging** | ☑ | ☑ |
| Allowed merge methods | **Squash** only | Team's choice |

**On a team, turn on Code Owners review for design.** A `CODEOWNERS` file can say that any change under `packages/tokens/` or `docs/decisions/` needs a designer's approval. That's the repository saying "design signs off on design", which is a stronger guarantee than any process document.

*Require conversation resolution* is the habit that makes a solo PR feel like a team one: every review comment, Claude's included, has to be resolved before merging.

Two repo settings go with it (Settings → General → Pull Requests): allow **squash merging** only, and turn on **Automatically delete head branches**.

**Test it:** commit a small change on `main` and run `git push origin main`. It should be rejected with a message telling me to open a PR.

## 4 · Connect Claude: /install-github-app

Run it inside Claude Code, in the repo (it needs `gh` signed in and admin access to the repo). It installs the Claude GitHub App, stores the secret, and pushes a branch with the workflow files, ready to open as a PR.

**Auth choice:**

| Secret | Billed to | Best for |
|---|---|---|
| `ANTHROPIC_API_KEY` | The Claude Console (API billing) | Shared or organisation repos |
| `CLAUDE_CODE_OAUTH_TOKEN` (from `claude setup-token`) | My Pro or Max plan | Personal repos |

When it asks, I pick both workflows: the `@claude` workflow and the review workflow.

## 5 · Merge the setup PR, then test it

Workflows only run once they're on `main`. Merge the PR it opened, then comment on any PR:

```text
@claude explain this diff in terms a designer would use
```

## 6 · Add CI, including a design check

CI (continuous integration) runs checks on every pull request and turns it red or green. For most repos that means build, lint and type checks. For a design system, it's also where a design rule can become impossible to break.

Mine runs four things: install, build, lint and type check.

```yaml
# .github/workflows/ci.yml
name: CI

on:
  pull_request:
  push:
    branches: [main]

jobs:
  build-lint-typecheck:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: pnpm/action-setup@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 22
          cache: pnpm
      - run: pnpm install --frozen-lockfile
      - run: pnpm build
      - run: pnpm lint
      - run: pnpm typecheck
```

The design check hides inside `pnpm lint`. The repo has one small custom lint rule, `no-token-escape`, which fails on a hardcoded value inside a Tailwind class: `p-[14px]`, `text-[#0c66e4]`, `rounded-[8px]`. Values that use a token, like `rounded-[min(var(--radius-md),10px)]`, are allowed. A hardcoded value where a token should be is the smallest unit of design-system decay, and it's easy to detect in code. In Figma you'd catch it by eye, if at all.

The build step matters too: it regenerates the tokens from the token file, so a broken or inconsistent token file fails the PR instead of reaching the docs site.

**What CI can't check:** how anything looks. I don't have visual regression tests in this repo, so the visual check stays in the inner loop (Part 1, step 4). If your team has the budget, screenshot-comparison testing is the natural next layer.

Once CI has run once, its job name (`build-lint-typecheck`) can be picked as a **required status check** in the ruleset. A red check is also what auto-fix reacts to (Part 3).

## 7 · Cloud sessions and auto-fix

Connect GitHub at [claude.ai/code](https://claude.ai/code) and make sure the [Claude GitHub App](https://github.com/apps/claude) is installed with **Only select repositories → this repo**. (Alternatively, `/web-setup` sends my local `gh` token instead, but auto-fix still needs the app.) Then set up the cloud environment:

| Setting | My choice | Why |
|---|---|---|
| Network access | **Trusted** (the default) | Package registries and common dev hosts work; arbitrary hosts don't |
| Environment variables | **No** cloud-provider or production credentials | A cloud session should never be able to touch live infrastructure |
| Setup script | Empty until I need one | The project's own `pnpm` scripts install what each task needs |

Remember that cloud sessions can't reach Figma. Give them repo-only tasks: stories, docs pages, translations, variants that are already specified.

The two workflow files that `/install-github-app` creates are worth reading once, so you know what's running.

### The `@claude` workflow (`.github/workflows/claude.yml`)

```yaml
name: Claude Code
on:
  issue_comment:
    types: [created]               # PR and issue conversation comments
  pull_request_review_comment:
    types: [created]               # inline diff comments
jobs:
  claude:
    if: contains(github.event.comment.body, '@claude')   # don't start a runner for every comment
    runs-on: ubuntu-latest
    permissions:
      contents: write
      pull-requests: write
      issues: write
      id-token: write              # needed for the default GitHub App auth
      actions: read                # lets Claude read CI results
    steps:
      - uses: actions/checkout@v6
        with:
          fetch-depth: 1
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          # or: claude_code_oauth_token: ${{ secrets.CLAUDE_CODE_OAUTH_TOKEN }}
          # trigger_phrase: "@claude"   # change it if managed Code Review also runs
          # claude_args: --max-turns 5
```

This minimal version only listens to comments. To trigger from a new issue's body or a review summary, start from the fuller [`examples/claude.yml`](https://github.com/anthropics/claude-code-action/blob/main/examples/claude.yml).

### The review workflow (`.github/workflows/claude-code-review.yml`)

```yaml
name: Code Review
on:
  pull_request:
    types: [opened, synchronize, ready_for_review, reopened]
jobs:
  review:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: read
      issues: read
      id-token: write
    steps:
      - uses: actions/checkout@v6
        with:
          fetch-depth: 1
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          plugin_marketplaces: "https://github.com/anthropics/claude-code.git"
          plugins: "code-review@claude-code-plugins"
          prompt: "/code-review:code-review --comment ${{ github.repository }}/pull/${{ github.event.pull_request.number }}"
          claude_args: '--allowedTools "mcp__github_inline_comment__create_inline_comment"'
```

Same Action, two modes: **no `prompt`** = interactive (waits for `@claude`); **with `prompt`** = automation (runs on the event). `--comment` is what makes the review post on the PR, and the `claude_args` line is what lets it.

## When setup misbehaves

| Symptom | Likely cause → fix |
|---|---|
| Ruleset saved but `main` still accepts direct pushes | Enforcement left on *Disabled*, or a private repo on GitHub Free |
| Can't merge my own PR | Required approvals > 0 on a solo repo → set it to 0 |
| Merge button blocked with no failing check | *Require conversation resolution* is on → resolve the remaining threads |
| Components render unstyled, but the build passes | In a monorepo, Tailwind v4 may not scan the component package for class names → add an explicit `@source` for it in the app's CSS. A screenshot catches this; CI doesn't |
| CI doesn't run on Claude's commits | `github_token: ${{ secrets.GITHUB_TOKEN }}` is set; GitHub doesn't trigger workflows from it → remove it so the Action uses the Claude App |
| `claude --cloud` works on old code | It cloned the GitHub branch, not my working copy → push first |
| A cloud session can't read the Figma file | Expected: the Figma MCP connection is local → do Figma steps on the laptop |

## Practise on a sandbox repo first

What made this click for me was a throwaway repo and a week of deliberately boring changes. For a designer, I'd make them design changes:

1. Do the setup above on a sandbox repo with a tiny token file and two components.
2. Make three tiny PRs with only `git` and `gh` (rename a token, change a radius, fix a typo in the docs) until branch → push → PR → merge is automatic.
3. Add a component variant with `/plan`, look at it in the browser, then run `/code-review` at `low` and at `high` and compare what each finds.
4. Hardcode a colour on purpose and watch the lint check go red. Then fix it with `/autofix-pr`.
5. Let the review workflow comment, try `@claude` for a fix, and resolve the threads.

None of these pieces is clever on its own. Together, they mean every change to the design system, mine or Claude's, reaches `main` through a pull request that has been checked and reviewed. That's the outer loop from [Part 1](/posts/design-in-git/design-in-git-part-1-explore-privately-critique-in-public), enforced by the repository instead of by memory.
